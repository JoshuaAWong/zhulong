## 1. 当前状态

- 烛龙现有实现为 Python + psutil + SQLite + 原生 HTML/JS 面板，系统监控、异常判定和处置安全链已可用。
- 公开化整理已完成：解释器安装/运行闭环、MIT LICENSE、隐私与安全说明、第三方许可证、文档清理、扩充 `.gitignore`，全量测试 17/17 绿。
- 本机 TokenTracker 已核实为：`.NET 8 WinForms + WPF + WebView2` 桌面壳，内嵌 Node 本地服务，React + Vite + TypeScript + Tailwind 仪表盘；源码与文档在 GitHub 项目内。
- TokenTracker 的功能范围不仅是 token 统计，还包括 46 个 AI 工具解析、费用与额度、桌面宠物、4 个挂件、15 条成就线、可选云同步/排行榜/Skills 管理。

## 2. 目标与评价标准

后续架构按以下优先级评估：

1. 轻量常驻资源、关闭面板后可回落到后台基线。
2. 高运行效率，避免无意义的常驻进程与定时刷新。
3. 高可靠性：故障隔离、可恢复、可验证、可回滚。
4. 维护复杂度可控，架构边界清晰。
5. 框架成熟、文档完善，适合 AI 实现与长期维护。
6. 隐私与安全：本地优先、动作白名单、云端功能默认关闭。

## 3. 讨论演变与结论

### 3.1 桌面壳选型

- 浏览器 App 模式：适合零成本验证，但不是正式架构。
- pywebview：适合简单 Python 窗口壳，不适合后续复杂托盘、挂件和进程监管。
- Electron：自带 Chromium 与 Node，多进程开销不符合轻量目标，不采用。
- Flutter/全原生 UI：两套复杂仪表盘重写代价大，不作为第一阶段方案。
- Tauri 2：轻量、现代，适合跨平台；Windows 专用时不是默认首选。

### 3.2 双引擎与统一后台

- 曾考虑以 TokenTracker 为上游骨架，保留 Node + Python 双引擎。优点是能快速兼容，缺点是生命周期、文档与维护成本较高。
- 也曾考虑以 Node 统一后台。其主要优势仍是保留 TokenTracker 现有代码，而不是最适合 Windows 系统监控。
- 用户明确两套旧实现均可重写后，结论调整为：**不为兼容保留双引擎，按领域需求重新设计统一后台。**

## 4. 推荐目标架构（Windows 优先）

采用 **.NET 10 模块化单体**：桌面壳、系统监控、AI 用量解析和本地 API 统一在 C#/.NET 内，不再保留 Python 或 Node 常驻后台。

```text
Zhulong.sln
│
├─ Zhulong.Core
│   ├─ 指标与用量数据模型
│   ├─ 调度器、规则引擎、动作安全链
│   ├─ 插件接口与依赖注入
│   └─ SQLite、迁移与保留策略
│
├─ Zhulong.Platform.Windows
│   ├─ GetPerformanceInfo / 进程 / 服务 / 绑核
│   ├─ EmptyWorkingSet / nvidia-smi / 网络采集
│   └─ Windows 通知与计划任务
│
├─ Zhulong.Providers.AI
│   ├─ AI 工具日志解析器插件
│   ├─ 去重、费用、额度与成就
│   └─ 厂商差异适配
│
├─ Zhulong.Desktop
│   ├─ WPF + WebView2
│   ├─ 托盘、窗口、桌面宠物、挂件
│   ├─ 单实例与进程生命周期
│   └─ 更新与安装
│
└─ Zhulong.Web
    └─ React + Vite + TypeScript 统一仪表盘
```

### 核心约束

- `Zhulong.Core` 不直接调用 Windows API，平台能力通过接口注入，便于测试和未来扩展。
- 一个后台进程；WebView 仅承担 UI，不再保留 Python/Node 两个常驻引擎。
- 系统指标采集器与 AI 日志提供器使用不同数据模型，但共享调度、存储、展示与文档基础设施。
- 桌面窗口与后台解耦：关闭窗口销毁 WebView，后台继续采集；重开恢复页面状态。
- 桌面端优先使用 WebView2 原生桥接；浏览器备用入口才保留 loopback API。
- 云端同步、排行榜和厂商额度远程查询继续默认关闭，必须用户主动开启。

## 5. 为什么选 .NET 而不是 Node/Tauri

- 应用同时依赖深度 Windows 交互与复杂日志解析；.NET 在前者最成熟，后者可由 System.Text.Json、SQLite、HttpClient 和 React 覆盖。
- 一个后台技术体系：异常、日志、进程监管、安装升级和文档统一。
- Windows API 无需跨语言桥接，commit、进程优先级、绑核、EmptyWorkingSet 和服务控制可直接实现。
- .NET 10 是 LTS，官方文档完整，适合 AI 长期维护。
- Tauri 2 仍是跨平台备选：若一开始要求 Windows/macOS/Linux 三端同等支持，可改选 Tauri 2 + Rust，模块边界沿用本文件。
- 若未来才需要跨平台，可保持 `Zhulong.Core` 平台无关，再增加 Avalonia 主机复用核心。

## 6. 推荐实施顺序（垂直切片）

1. **系统监控 MVP**：commit、CPU、磁盘、网络和基础面板，先验证 Windows 适配层。
2. **单个 AI 提供器闭环**：优先 Kimi Code，完成日志 → 用量 → 图表。
3. **AI 提供器插件体系**：复用 TokenTracker 的测试样例做 golden fixtures，再逐个扩展，禁止一开始同时重写 46 个提供器。
4. **宠物、挂件、成就与可选云端功能**。
5. **安装包、自动更新、CI 与正式发布**。

每一步都必须可独立验收、可回滚，不做一次性大爆炸重写。

## 7. 验收基线

- 新旧实现对同一批系统指标逐项对账，不能只验证“页面能显示”。
- AI 解析用 TokenTracker 的样例与真实日志做 golden fixtures，重点验证去重、缓存 token、费用语义。
- 连续开关窗口 100 次无异常；关闭面板后无残留 WebView 进程。
- 长时间挂机无内存/句柄持续增长；后台 CPU 与内存不高于约定基线。
- kill/内存整理/服务重启等动作安全链必须在测试环境真实触发降级路径。
- 默认无云端请求；所有外部网络访问均可枚举、可关闭。

## 8. 尚未拍板的问题

1. **平台范围**：只做 Windows、Windows 优先，还是一开始要求三端？这会直接影响 .NET 与 Tauri 的选择。
2. **云端范围**：是否包含排行榜、跨设备同步、Skills 管理和厂商额度远程查询；默认建议全部保留为可选关闭项。
3. **旧数据迁移**：是否导入现有 `zhulong.db` 和 TokenTracker 历史用量，还是从新数据库开始。
4. **AI 提供器覆盖顺序**：Kimi Code 之后优先哪些工具，以本机实际使用情况还是用户使用人数排序。
5. **资源硬指标**：后台内存、CPU、面板打开时峰值和安装包大小的具体预算，需要 MVP 实测后确定。
6. **旧版本迁移**：现有 Python 烛龙和 TokenTracker 的共存、停用与卸载流程。
7. **发布方式**：便携包还是安装器；是否内嵌 .NET 运行时；自动更新渠道与签名策略。
