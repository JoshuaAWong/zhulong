## 1. 选型结论与比较

采用 C# / .NET 10 LTS 模块化单体，Windows 原生适配、统一后台、SQLite，WPF 管理桌面生命周期，React + TypeScript + Vite 构建复杂面板，WebView2 按需承载。框架选择不构成性能达标证明。

| 路线 | 适用性与取舍 | 本次结论 |
|---|---|---|
| 继续维护 Python | 改动最少，适合只修现有问题；已有采集/规则/安全链可作对照 | 保留为过渡与回归基线 |
| .NET + 原生 WPF 全界面 | 无浏览器引擎开销；可做原生动效，复杂图表和既有 Web 风格需重做 | 保留为完整面板对照；不能仅凭少一个运行时就宣称所有场景更快 |
| .NET + WPF/WebView2 | Windows 能力集中，复用 Web 表达，生命周期可控 | 目标方案 |
| Tauri 2 + Rust | 适合三端同等优先；Windows 仍使用 WebView2，并非天然只有一个进程 | 未来跨平台需求改变时再评估 |
| Electron 或保留 Python+Node 双后台 | 能复用更多上游代码，但增加常驻运行时和生命周期边界 | 不作为统一后台方案 |

.NET 10 的 LTS 支持期截至 2028-11-14，采用仍受支持的补丁版本。[官方支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)
WebView2 使用多进程引擎；官方建议避免冗余实例并释放不用的控制器。[性能指南](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
Tauri 的跨平台核心和各平台 WebView 分工见[官方进程模型](https://v2.tauri.app/concept/process-model/)。

P0-A 使用 [独立实验宿主](../prototypes/p0-ui/README.md) 对照同负载 WPF 与 WebView2/React。只实现界面生命周期，不把实验的合成数据、简化图形或构建器当作正式业务设计。当前结果及限制由 [P0-A 记录](P0界面对照验证.md) 维护。

DEC-10 将综合性能、低开销与动效并列为目标。工程分工是“常驻部分原生、复杂面板按需”：动效本身不构成引入 WebView 的理由；混合方案的收益是复杂面板表达与开发维护成本，代价是开窗时的浏览器资源和启动时间。若同等内容/动效下混合方案不能满足预算，P0-E 提出纯 WPF 调整建议并更新 DEC-03，不能默默降低体验或宣称当前组合性能最优。

## 2. 模块边界

下表是逻辑边界，实施时按实际需要划分项目，避免为每个接口创建独立程序集。

| 模块 | 唯一职责与所有权 | 禁止越界 |
|---|---|---|
| Zhulong.Core | 系统指标/AI 用量领域模型、规则、动作请求/结果契约 | 不访问 UI、数据库和 Windows API |
| Zhulong.Application | 调度、最新快照、用例编排、动作授权与生命周期协调 | 不解析厂商日志、不直接 P/Invoke |
| Zhulong.Platform.Windows | 系统采集、进程/服务操作、进程身份与保护证据 | 不自行决定是否执行规则动作 |
| Zhulong.Providers.AI | 每个工具的发现、解析、增量游标、去重和额度适配 | 不操作系统进程、不持有界面、不各自启动永久循环 |
| Zhulong.Storage | SQLite 表、索引、事务、版本迁移与保留策略 | 其他模块不绕过它写库 |
| Zhulong.Desktop | WPF 宿主、托盘、窗口、通知适配、宠物/挂件与受限消息桥 | 不重写规则和采集逻辑 |
| Zhulong.Web | React 展示、交互状态、图表及中文解释 | 不持有本机凭据、不任意读文件或执行命令 |

依赖向 Core 的模型和接口收敛，Desktop 作为组装入口注入适配器；AI 数据与系统指标不强塞进同一个万能模型。不开微服务、消息服务器或运行时插件市场；提供器先作为内置模块注册。

## 3. 进程、权限与窗口生命周期

- 一个常驻业务主进程；托盘 UI 在消息线程，采集、解析、存储不在 UI 线程运行。
- WebView2 自有浏览器/渲染/GPU 子进程计入应用资源总账，不能以“一个后台”宣传为“全应用一个进程”。
- 初始启动先建立托盘和后台；打开复杂面板才创建 WebView。关闭面板解绑事件、停止展示刷新并 Dispose，重开由最新快照恢复状态。
- 轻量挂件/宠物优先原生承载，动画只在可见且启用时运行。若未来挂件必须使用 WebView，单列实例预算与生命周期；验收区分“主面板关闭”和“全部 WebView 关闭”。
- 退出与重启走同一资源释放属主：停止接单、停止调度、完成或取消在途任务、完成写库、还原可恢复的限流、释放控制器与自有辅助进程。主动退出意图和重启意图区分。
- 辅助命令按需启动，限定超时并跟踪所有权；只清理本应用创建的进程。取消令牌不能强行取消任意阻塞原生调用，确需隔离的适配器须在其阶段说明进程边界。
- 普通用户权限运行，不设常驻管理员服务。当前阶段不引入提权或驱动。服务重启、受保护进程等能力按实际权限报告可用/不可用；P3 分别记录拒绝与成功证据，不能用一次 AccessDenied 测试代替动作能力验收。

### 3.1 低开销动效与渲染责任（DEC-10）

- **原生承载**：托盘交互、轻窗口、挂件与二维宠物优先 WPF；用现有动画/时间线能力做淡入、位移、缩放和状态切换。WPF 自带属性动画与 Storyboard，不因“需要动效”增加浏览器或游戏引擎。[官方动画概述](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/animation-overview)
- **复杂面板**：沿用 React/TypeScript + 按需 WebView2；主面板内切换视图，避免给每张卡片/小挂件单开 WebView。后台启动不预热浏览器，关闭面板释放而非无限保活；接受再次打开存在初始化成本，实测后再权衡。[WebView2 性能指南](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
- **独立时钟**：Application 负责数据采集频率，Desktop/Web 只在动画活动时推进视觉帧；不以 30/60 帧每秒调用采集器、查询数据库或跨消息桥传数据。曲线过渡只插值显示，原始时间戳、数值、落库和规则判定不变；没有新数据时不制造实时变化，后台扫描不占 UI 线程。
- **按需绘制**：优先改变现有 RenderTransform 等视觉属性，减少反复触发布局；静态背景与装饰不进入持续循环。Web 动画局部更新，不每帧重建整页 React 状态。阴影、模糊、透明叠层的实际成本纳入测量，不承诺所有效果都由 GPU 免费完成。[WPF 布局性能指南](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design)
- **统一生命周期**：由 Desktop 的窗口生命周期协调可见状态，Web 接收同一状态并停止自己的动画；不只依赖浏览器后台节流。UI 失去焦点不等于隐藏，仍可见的监控/宠物应按设定正常显示。提供减少动效选项并尊重系统相关偏好，状态与告警不能仅靠动画传达。

| 界面状态 | 允许工作 | 停止或释放 |
|---|---|---|
| 可见、无动画活动 | 新快照到达时更新必要区域 | 无应用自建永久逐帧循环 |
| 可见、正在交互或播放动画 | 局部动画；仅展示已收到的数据 | 动画完成后移除计时/渲染订阅，不累计时钟对象 |
| 隐藏、最小化或会话锁定 | 业务后台按原频率采集/记录 | 暂停对应界面动画和 UI 刷新订阅；恢复时读最新快照，不补播积压帧 |
| 减少动效 | 静态替代、必要状态提示和数据更新 | 关闭装饰性循环和大幅位移，功能信息不丢失 |
| 关闭界面 | 业务后台继续；其他可见界面独立运行 | 取消该界面任务/事件/动画时钟；Dispose 自有 WebView，按 N-02 观测退出，不强制结束其他应用进程 |

候选测量目标：以 60 Hz 显示环境下的交互过渡 60 fps、持续二维宠物动画上限 30 fps 起测；这是工程候选值，不是用户已确认预算或达标结果。正式对照前锁定动作时长、素材大小、点数、DPI、分辨率、刷新率及渲染路径，报告帧耗时 P95/P99、长帧和采样延迟，而非只看平均 FPS。虚拟机若只有软件渲染，只能证明该环境的结果，不能外推本机 GPU 表现。视觉复杂度与预算冲突时先交付对比证据，再由 Q-05 决定取舍。

## 4. 调度与数据通路

系统采样与 AI 解析使用同一调度属主、不同任务队列和频率。关键水位采样不等待 AI 历史补扫，单个任务只允许一次在途执行；积压时合并重复刷新请求，不无上限创建 Task 或线程。

建议采用 .NET 标准计时、CancellationToken 与有界 Channel；并发度按任务成本定标。有限队列用于限制积压，不是用来丢掉关键动作或审计记录。

数据通路：

1. Windows 采集器输出带单位、时间、来源和有效状态的样本；同周期进程快照按需复用。
2. Application 发布不可变最新快照，供托盘、规则和面板读取；旧样本必须显示陈旧或失败状态。
3. Storage 批量保存历史；规则评估不必反复查库取得刚采集的值。
4. AI 解析器将标准化记录、游标和去重依据交给事务边界；提交成功后才能推进持久游标。
5. UI 订阅必要变化，隐藏/关闭时取消订阅；历史查询限制时间范围和返回点数。

计划保留系统基础 30 秒、较重进程采样分频的现有语义，具体频率在 P0/P1 对账后固化。初次扫描、增量刷新、历史修复各有预算，不能用无限并发掩盖全量扫描成本。

### 4.1 关键契约草案与唯一属主

以下字段表达语义，接口签名由对应切片落实，不提前生成通用框架。

| 契约 | 必要信息与行为 | 属主 |
|---|---|---|
| MetricSample / Snapshot | 指标名、单位、来源、采样时间、值及状态；缺失/不支持/失败/陈旧不填成 0；快照有修订号，同一周期复用进程快照 | Core 定义，Application 发布 |
| ProcessIdentity | PID + 原生创建时间；后续动作重新核验同一实例，不截断时间精度，不把进程名当实例身份 | Platform.Windows 提供证据 |
| UsageRecord | 工具、来源、会话/事件身份、模型、时间、各 token 项、费用类型及价格版本；本地估算与账单实际费用分别标注 | Providers.AI 标准化，Storage 保存 |
| ActionRequest / Result | 请求标识、自动/手动来源、白名单动作、目标实例；拒绝、执行成功、执行失败及部分完成可区分，不因超时自动重放破坏性动作 | Application 统一执行，Platform.Windows 实施 |
| ViewRequest / SnapshotUpdate | 协议版本、请求标识、允许的消息类型与结构化参数；关闭时注销订阅，过期页面的回复不再更新新页面 | Desktop 桥接，Web 展示 |

调度只合并可替代的快照/刷新请求；动作结果、AI 账本与持久游标不能按“队列满了就丢弃”处理。历史补扫分批提交并让出写入时段，查询限制时间/点数；具体批量与等待期限由 P0-C 定标。前端只保留可见查询结果与交互状态，不复制完整历史账本；分析/规则只读 Application 的业务快照，避免 UI 另算一套结论。

CLI 默认通过受当前用户权限限制的本地命名管道调用同一只读查询用例，不再建常驻服务；宿主未运行时诊断只读打开新库，不启动自动处置。浏览器入口属于现有能力承接，按用户显式打开时启用 loopback 服务并复用查询/动作入口；桌面面板不依赖 HTTP 服务才能运行。

## 5. AI 提供器契约

每个提供器描述工具身份、发现路径、支持的数据源、增量策略和能力边界；独立解析为统一用量记录。目录结构与接口签名在首个提供器切片中确定，当前顺序沿用 Kimi Code，待需求 Q-04 收口；之后由第二个提供器检验是否确有复用价值。

- 文件游标包含来源身份、文件身份和已提交偏移；处理追加、截断、轮换、同大小重写及末尾未写完的一行。
- 文件监听仅作变化提示；配合有界的周期校准，不能把监听事件当成绝不丢失的事实源。
- 去重依据采用提供器真实事件/会话身份，处理 Native/WSL 重复来源、累计量事件与历史修正，避免一条事件被计两次。
- token 输入/输出/缓存/推理口径逐提供器对账；未知值不填零，不用通用加法猜厂商语义。
- 费用保留价格来源、版本和估算状态；金额使用明确精度。额度远程查询与本地用量采集分开调度，凭据只留在受保护的后台存储。
- 队列容量、缓存容量、全量扫描周期、重写检测策略必须有可测说明；不把“增量解析”直接等同于“只读取新增字节”。

TokenTracker 的解析语义、Windows 宿主经验与测试样例可参考；Token Monitor 的采集隔离、活动调度和同步契约可参考。只迁移需要的能力并保留适用许可，不引入它们完整运行时：
[TokenTracker 核查版本](https://github.com/xiufengsun/TokenTracker/tree/905a54e89b8bf42b0dd19bcd0bfb40d3fca92e3d)、
[Token Monitor 核查版本](https://github.com/Javis603/token-monitor/tree/9e0d0e97e59dfb5732eb4b2a2626e7e5219f05d5)。

## 6. 存储与时间语义

SQLite WAL；优先单写入属主、短事务、独立受限读取，采用 Microsoft.Data.Sqlite 与显式 SQL。先不引入 ORM、外部时序数据库和服务端缓存。实际表、索引和迁移脚本在 P1/P2 分别设计。

系统指标、AI 用量账本、采集游标、动作记录和配置状态分别建模。高频指标可以合批/按变化记录，动作和账本记录不能静默丢弃；写入失败必须呈现未持久化状态。

窗口持续时间、冷却与调度使用单调时钟；持久事件使用 UTC 墙钟，展示按本地时区。跨重启静音期限用持久墙钟单独建模；休眠恢复重新采样并避免用陈旧值立即触发动作。

新数据库使用独立目录及 schema 版本。旧记录保持原样；Q-03 确定前不设计自动覆盖迁移。任何导入必须处理旧版本地时间、指标改名、重复记录与费用语义，并可在数据副本上回滚。

### 6.1 存储实体与提交边界

| 实体组（候选名称） | 内容与约束 | 阶段 |
|---|---|---|
| metric_samples / action_events | 指标及质量状态；动作意图与实际结果分开记录；指标按名称/来源/时间查询 | P1 / P3 |
| usage_records / source_cursors | 用量事实与来源位置在同一事务提交；文件截断/重建产生新一代来源，旧偏移不能直接套用 | P2 |
| price_versions / usage_costs | 价格币种、计价单位、适用日期、出处及估算口径；重新估算产生可辨认版本，不伪装成原账单 | P2 |
| import_batches / import_items | 源库摘要、源表/行身份、映射版本、导入结果和校验统计；同一来源重复导入幂等 | Q-03 选择导入时，P4 |
| schema_migrations / app_state | schema 版本及迁移记录；配置/展示状态与机器相关运行状态分开 | P1 |

SQLite 主库先承载这些逻辑实体，不按模块拆成多库；表和索引随切片创建，不一次建齐。写入连接仅由 Storage 的串行写入任务使用，读取使用短连接/受限读取；不跨线程并发使用同一连接。UI 刷新不直接写库。

旧 `core/storage.py` 已使用 WAL，`metrics/events/kv` 是当前表；`scheduler.now_iso()` 写的是无时区本地时间。迁移必须保留来源时间文本，明确源时区及不确定记录；不能直接把旧时间当 UTC。旧进程 PID、限流已施加清单、看门狗意图和熔断内存状态不作为可执行命令导入；配置迁移与历史导入分别预览。

### 6.2 历史接入草案（受 Q-03 约束）

推荐导入路线：选择来源 → 读取版本/表结构并报告支持范围 → 取得一致性快照 → 预览条数/时间范围/时区/重复项 → 用户确认 → 分批事务导入新库 → 独立对账与批次结果。任一步失败不改源库；未完成批次可按记录续入或撤回该批次，不覆盖之后采集的新数据。只读查看/仅归档方案分别省去写入步骤/不建立接入模块，不能同时承诺三套实现。

AI 去重优先使用工具真实事件身份；文件路径只是来源位置，复制日志到 WSL 或另一目录不应自动变成新用量。累计 token 事件按提供器定义转换为增量或修订，不直接逐行相加；缺少可信身份的跨来源记录标注不确定，不能依据文本或相近时间强行合并。原始对话正文不随统计导入；必要错误样例脱敏，测试夹具不得包含用户真实密钥/完整会话。

备份优先使用 SQLite 备份接口生成一致性副本；不要在源库运行时仅复制 `.db`。Microsoft.Data.Sqlite 的 `BackupDatabase` 会阻塞其他连接写入，不能宣传为无代价后台操作；源库备份需受控安排，不以导入为由长期阻塞旧监控。[官方备份说明](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/backup)

保留期由 Q-12 收口；当前旧版 `cleanup()` 同时清理 30 天前的 metrics 与 events，不能误记成只清指标。AI 账本不继承该清理规则；数据归档、程序升级备份和运行缓存分别管理，不由一条通配删除覆盖。

## 7. 安全与动作入口

- 所有动作由同一授权/执行入口接收结构化请求，自动与手动共用保护规则和熔断；UI 仅提供意图，不能决定安全检查已通过。
- 保留 NEVER_KILL、安全软件/系统/自身保护、白名单、配置路径时 fail-closed、重读水位、存活时长、创建时间竞态检查、执行后记账及降级。新语言不能削弱既有顺序与拒绝条件。
- 内存整理只回收 working set；服务操作遵守服务白名单、重启失败恢复和可见结果；不可把终止宿主进程当作通用服务重启。
- WebView 消息桥限定可信本地页面、来源校验、会话令牌、消息类型和动作白名单；不暴露任意文件/命令/配置写接口。凭据不进入前端状态或日志。
- 浏览器备用入口如保留，仍只绑 127.0.0.1，静态资源字面白名单，仅 GET 查询与受 CSRF + Host/Origin 校验的 POST /api/action；端口失败不得拖垮监控。
- 默认关闭可选云端功能；网络探测、更新、远程额度及同步逐项登记目标、数据和开关。不能将“本地优先”表述为没有任何网络请求。

### 8.1 同一核心、两种交付

- CI 对同一源码版本构建核心程序，再由该产物生成安装包和便携压缩包；版本号及数据 schema 一致。安装器只承担部署集成，不复制业务逻辑。
- 安装版提供程序部署、快捷方式、必要运行环境处理及卸载入口；自启等系统集成由用户选择，不因首次运行自动开启。
- 便携版以解压运行交付，不要求运行安装器。程序、可迁移数据、缓存和机器绑定状态分别定义，不能仅因为是压缩包就宣称所有状态都可跨机器复制。
- 工程建议采用自包含 .NET 发布，避免用户先装 .NET；自包含会增加分发体积，并需要随应用维护运行时补丁，不等于增加独立常驻服务。[.NET 发布方式](https://learn.microsoft.com/en-us/dotnet/core/deploying/)
- WebView2 Runtime 单独处理，不能把自包含 .NET 等同于包含 WebView2。优先检测系统 Evergreen Runtime；缺失时明确引导，不静默安装。完全离线便携是否携带固定版本 Runtime，按体积和更新成本在发布详细计划中决定。[WebView2 分发](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- 两种形态均需区分程序文件与数据：升级不能覆盖用户配置/数据库，卸载或删除程序前须明确数据保留位置；启用过自启时提供取消入口。

### 8.2 更新流程边界（DEC-09 已确认）

用户已确认更新包下载到程序目录的 updates 子目录，确认后更新；安装版使用安装包，便携版使用对应压缩包。两种交付共用更新检查、版本和包核验逻辑，应用替换步骤按交付类型执行。确认前不得运行安装包或替换程序文件。

详细设计按已确认流程补齐：更新检查/下载触发、确认界面、包与版本核验、程序目录不可写时的明确提示、退出后替换文件、失败恢复旧版本，以及升级后的数据 schema 回滚。目录不可写时不得悄悄改用其他位置或自动提权。不能边运行边覆盖在用文件；更新包落地位置不等于安装目标或数据目录，也不因便携版收到更新而将其静默转换为安装版。

### 8.3 程序、数据与机器状态布局（工程建议）

| 路径角色 | 安装版建议 | 便携版建议 | 更新/迁移约束 |
|---|---|---|---|
| 程序目录 | 默认当前用户 `%LOCALAPPDATA%/Programs/Zhulong`，可选择可写目录 | 解压目录 | 常规运行无需管理员权限；目录不可写明确提示 |
| 数据根目录 | `%LOCALAPPDATA%/Zhulong` | 程序目录下 `data` | 存放新库、配置与业务历史；不与旧 Python 数据目录混用 |
| 下载包 | 程序目录下 `updates` | 程序目录下 `updates` | 严格遵循 DEC-09，不静默另选位置 |
| 缓存/日志 | 数据根下 `cache` / `logs` | 同左 | WebView 用户目录归本应用管理；停止相关进程后才能清理 |
| 备份/机器状态 | 数据根下 `backups` / `state` | 同左 | 数据备份保留；自启路径、运行锁和凭据不能视为跨机器可复用状态 |

发行物显式标记安装/便携模式，不能靠“碰巧有 data 目录”猜测。安装版和便携版共用产品单实例规则及动作属主，第二份程序不得同时接管自动处置；开发隔离实例只用测试目录并禁用处置。移动便携目录前完整退出；移动后重新处理自启路径，换机器重新授权凭据，不自动搬运或明文降级保护。卸载默认保留数据，删除数据必须另行明确选择。

此默认安装布局使程序目录内 updates 在通常情况下可写；若改为 Program Files 或全机安装，权限/更新方式须重新评估，不能在普通用户运行方案里暗含提权。便携目录应在本地磁盘使用，网络共享盘上的 SQLite/WAL 不列入首版保证范围。

### 8.4 更新状态与失败恢复草案

检查/下载触发由 Q-11 决定。共用状态为：发现新版本 → 下载到 updates 临时文件 → 校验完成 → 待用户确认 → 停止接单并退出 → 安装/替换 → 新版本健康检查 → 完成。确认前可以按已选择策略下载，但不可执行更新；用户取消则保留当前运行版本。

1. 发布清单绑定版本、平台、架构、安装/便携类型、包摘要与 schema 兼容范围；包摘要证明内容一致性，真实性另由可信发布签名保证。建议签名清单配内置公钥；证书/密钥管理和更新渠道在 P6 发布计划冻结，未完成不得把自动更新标为可用。
2. 更新前确认空间和目录权限，停止调度、完成写库并保存配置/数据库的一致性备份。退出等待有期限，仍有自有进程占用则中止替换并展示原因，不盲杀进程。更新过程中抑制自身看门狗拉起，最终按更新结果恢复启动意图。
3. 安装版交给同版本安装器；便携版由短命更新助手在主程序退出后操作。解压到暂存目录，验证路径只落在允许的程序文件范围，排除 data、updates 和备份，不直接覆盖用户目录。助手只负责换文件/恢复与结果记录，不运行采集业务。
4. 升级前保存旧程序与匹配的配置/数据库快照；新版本先验证 schema、核心查询和启动条件，再开启正常采集/动作。验证失败且尚未接收新业务写入时，可恢复整套旧版本快照；不能只回滚 exe 让旧程序打开新 schema。
5. 新版本开始产生数据后，不自动恢复旧数据库丢弃新记录。保留故障库与备份，明确展示差异，再按经过演练的恢复流程处理。回滚不是对运行中目录强行覆盖。

WebView Runtime、.NET 自包含运行时和应用本身分别记录版本与补丁责任；常规便携包是否提供离线完整变体由 Q-10 决定，不把缺运行时当成数据库损坏或主动安装权限。[.NET 发布说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/) · [WebView2 分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
