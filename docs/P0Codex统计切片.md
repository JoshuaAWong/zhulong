# P0-C：Codex 会话统计与套餐重置切片

日期：2026-11-08。独立命令行验证项目：[源码](../prototypes/p0-ai/README.md)。沿用 C#/.NET 10、统一 SQLite 账本，不启动 UI、监控动作或常驻采集进程。

## 方案与成功标准

本轮授权：参考 TokenTracker 做 Codex 会话统计，参考 Token Monitor 比较设计，控制开销；用户确认“刷新时间”指套餐额度重置时间和剩余等待。范围为本地 rollout 读取与离线额度快照，在线额度与正式界面接入分步推进。

自查（非独立把关）：大档数据契约切片，可独立验证。沿用既定 .NET/SQLite，不复制完整 Node/Electron/Tokscale 服务。新代码约千行含验收，按解析、扫描、存储和入口拆分；没有一次性建完所有架构模块。Microsoft.Data.Sqlite 是已定存储依赖，用原子事务提交事件、会话关联、额度及游标；不引入 ORM 或额外测试框架。底层原生 SQLite 版本须通过包漏洞审计。

硬门禁：人工核定的计数与额度时间相符；重复扫描/复制/分叉总账不翻倍；尾部半行和跨批状态正确；注入写入失败后重试不丢计；单批正文读取不超过4 MiB；未变化扫描正文与锚点均零读取；追加只读取新增正文及固定锚点；命令退出后无自有后台进程。

候选资源观察：固定大于10 MiB的合成日志，记录读取字节、批次数、单次耗时/CPU与末尾内存。耗时与内存本轮不设追认式通过阈值；不等同常驻、峰值、24小时或完整P0性能验收。

## 数据契约与开销

- session_meta/turn_context 保存会话、父关系和模型；累计token_count转换增量，最多32条累计基线处理交错流。输入包含缓存，输出包含推理，总量不再加子集。
- 普通 token_usage_record 与 token_count 不双计；压缩记录只有紧跟compacted且下一累计未增长时按response_id补计。只出现record的新格式保持RecordOnly警示，未声称全格式支持。
- 总账事件只计一次；usage_sessions另保存事件与会话关系。因此每会话包含其日志中回放/继承历史，不能再把各会话总量相加作为账户总量。总览读取唯一总账，扫描顺序不决定会话汇总归属。
- 普通token_count缺少稳定请求ID时，以原时间/模型/last/total/delta指纹去重；这是启发式身份，若两个独立事件所有字段完全相同可能合并，仍须真实脱敏样本对账。
- 文件按完整换行推进，4 MiB/批；命令总正文预算最多16 MiB，预算耗尽保留游标，下一次继续。末尾半行等待追加，超单批上限的行显式失败，游标不前进。
- 未变化由长度/mtime/creation识别，零正文读取；变化时读固定首尾锚，追加只读新增正文。截断、替换和同尺寸mtime变化重放去重；同尺寸且保留mtime的改写、历史中部改写同时追加尚无完整文件哈希证明，不列为已通过能力。
- SQLite单写事务覆盖用量、会话关联、额度和游标，写失败回滚。坏JSON完整行记数后跳过，半行不跳过；正文不写数据库。
- scan仅输出扫描摘要，report显式查询，最多各100行会话/来源/额度快照，统计总量来自唯一账本。全部历史汇总仍有SQL扫描成本，尚未做正式时间范围分页与增量聚合。

## 套餐重置语义

按日志中的limit_id、来源会话和primary/secondary分别保存已用比例、窗口分钟、resets_at、observed_at。日志没有可信账户身份时标记未知，不能合并成已确认账户；不同来源会话快照分别保留。

剩余等待为max(0,resets_at-now)，到期显示awaiting_refresh，仍保留旧比例；缺失时间为unknown_reset，未出现额度记录为空。日志快照没有新活动便不会主动更新；本轮没有OAuth/CLI在线额度查询，也不将token用量推算成套餐余额。

Token Monitor采用独立在线额度运行时、低频/手动和重置边界单次补刷，见[对比](TokenMonitor统计与额度设计对比.md)。后续在线切片明确账户与凭据范围后接入同一窗口契约，不能将离线倒计时说成已获得实时剩余额度。

本地rollout不覆盖所有Codex桌面任务，部分Dots聊天没有对应日志；不启用会恢复云端线程的补充采集方式。本切片不读取认证文件或对话正文到输出，不启动app-server。

## 验证与证据

运行时生成合成夹具，独立人工预期；验收脚本直接调用真实扫描/存储路径。最终结果：Release构建0警告0错误；self-test 94项断言通过，SQLite实际3.53.4；旧Python全量17/17通过。证据在忽略目录out/p0-ai/acceptance.json及合成fixtures，真实库和会话数据不提交。

| 合成负载指标 | 实测 |
|---|---|
| 来源大小 / 批次 | 13,320,601字节 / 4批 |
| 冷读正文 / 锚点 | 13,322,550 / 6,656字节；正文含1,949字节尾部半行重读 |
| 未变化正文 / 锚点 | 0 / 0字节 |
| 追加374字节 | 正文374 / 锚点2,048字节 |
| 单次冷扫描耗时 / CPU | 106.55ms / 93.75ms |
| 测试末尾private / working set | 49,655,808 / 80,240,640字节；非峰值、非常驻基线 |

本机只读实测取得2,499个会话累计快照。一份早先约478KB、当时没有usage的日志后续写入后，扫描630,423字节得到11个唯一事件及1组周额度；复扫0正文/0锚点读取。源库使用包含WAL的只读事务，测试进程正常退出。额度来源为日志历史快照，尚非在线账户查询。摘要out/p0-ai/live-summary.json、可查看报告out/p0-ai/live-report.json；不提交其中会话ID、路径或真实用量。

故障验收：SQLite trigger在事件或快照批次中途抛错，验证零部分写入且重试恢复；半行、截断、不同区域同尺寸重写、record-only、交错累计与压缩、过期/未知额度、不同来源会话快照均真实触发。扫描/存储的交叉只读审查修正了积压被误跳过、输出物化无界及会话归属随枚举顺序变化的问题。

## 回滚与后续

删除独立构建产物即可停止使用；没有生产替换或自启。新库在显式指定的新路径，源JSONL只读。故障注入后重开/重扫恢复已验证；完整存储备份恢复仍在P0-D。

下一步：脱敏真实格式对账与来源覆盖核验、在线额度独立读取、统一调度/界面消费。P0-A隔离桌面动效、P0-B原生指标、P0-C慢源与系统采样隔离、24小时稳定性等门禁仍未完成。

### 本机桌面格式补充

一份约478KB桌面rollout的结构检查未出现token_count/token_usage_record，只出现会话/响应/任务元数据。为避免把缺失当零，report提供not_observed及覆盖质量统计。Codex状态库threads.tokens_used可作每会话累计快照，官方提取器将其设置为total_token_usage.total_tokens；该来源不提供输入/缓存/输出拆分，不用于推算按日用量或费用，也不与请求总账相加。metadata命令只读源库并单事务更新新库快照，兼容源WAL；本轮已用只读实测取得当前源库快照，但仍不能把它当作按日账单。更正重写保留已观察旧事件，因此总账不是文件当前内容的镜像，历史修订需后续对账机制。

依赖验证发现旧native SQLite包NU1903，已显式约束SQLitePCLRaw.bundle_e_sqlite3 3.0.5并实际锁定SQLite 3.53.4，Release重新还原构建0警告0错误，未抑制审计。[漏洞公告](https://github.com/advisories/GHSA-2m69-gcr7-jv3q)、[bundle版本](https://www.nuget.org/packages/SQLitePCLRaw.bundle_e_sqlite3/3.0.5)。

官方固定版本依据：[tokens_used提取](https://github.com/openai/codex/blob/748ab55ca7de0b647d9a7a9d9a8e70e00f28666d/codex-rs/state/src/extract.rs#L133)。另已核实[account/usage/read在线处理](https://github.com/openai/codex/blob/748ab55ca7de0b647d9a7a9d9a8e70e00f28666d/codex-rs/app-server/src/request_processors/account_processor.rs#L1283)与account/rateLimits/read可作为后续有登录态的短命CLI适配候选，无需恢复线程。本轮未实现该在线进程协议；一次宿主只读额度查询返回不可用，未填造重置时间。

CLI额外验收：两个相同13.3MB日志构成大于26MB来源，首命令读取13,322,924B后预算停止，第二次续读剩余且无新增重复事件，第三次零读取，总量150符合人工样例。源/目标同路径命令在打开库前拒绝，合成源库SHA256前后相同；证据out/p0-ai/cli-acceptance.json。

拆分评估：Acceptance.cs约四百行，承担同一切片的夹具和并列断言，暂保留单runner以避免额外测试装配；生产代码按解析/扫描/存储/快照各自拆分，未超单文件职责边界。
