## 配置与指标口径

- 默认采样等待30秒；memory/cpu/diskio/net/process 每周期，GPU每2周期，proctop每4周期。loop 是工作结束后 wait(30)，因此实际周期还包含采集耗时，不能把30/60/120秒当实测精确频率。
- commit 读取 GetPerformanceInfo 的 CommitTotal/CommitLimit × PageSize；GB 字段按 1024³换算。pagefile 另由 psutil.swap_memory 提供；同一 collect 中 pagefile 抛错会使内存采集整组无返回，错误状态与缺失值需要对账，不能补零。
- 磁盘/网络速率按计数差分 / dt / 1024²，标作 MB/s，实际为二进制量级；当前 dt 用墙钟。新旧展示单位与计数窗口必须显式统一。
- 高水位 enter=85、exit=80，持续90秒，冷却600秒；单核规则为最忙核≥95且总占用<70，持续90秒。这些是旧版配置，不自动等于新版性能预算。
- metrics/events/kv 三表；metrics与events每日清理30天前记录。历史时间为本地无偏移 ISO 字符串；新版导入应保留来源时区/不确定性。
- AUTOKILL、RESTART_SERVICES 默认空；MEM_TRIM 有物理内存60%压力门槛。run_cycle 即使 evaluate=False 仍走限流/整理巡检，因此本轮只调用 build_ctx，不以“禁规则评估”冒充无动作运行。

## 已复现问题与迁移风险

1. **单核告警数据通路缺失（已复现，尚未修复）**：scheduler.build_ctx 只装入 memory 的4个指标，不装 cpu.cpu_max_core/cpu.cpu_percent；rules._single_core_hot 因缺值返回 false。2026-11-08 14:35:37 +08:00 用内存 SQLite 写入98%单核、20%总CPU，再调用实际 build_ctx：两字段均为 null，条件 false；直接构造同值 MetricCtx 时条件 true。只调用条件，不发送通知、不执行动作。现有 test_engine 注入了完整 CPU ctx，不能覆盖调度断链。需要另列小修及集成回归，未在本轮改生产代码。
2. **历史进程身份仍不完整（源码限制）**：proctop 内存缓存比较 create_time，但落库 label 不含启动时间；同名同PID跨生命周期的历史去重仍需验证。新版必须以进程实例为键。
3. **原型示例不对应现有指标**：页面“最忙磁盘8%”是固定样本；旧采集器只给吞吐与忙盘标签，正式接线前应补指标来源或明确不提供。
4. **异常隔离不等于慢调用隔离**：GPU查询与网络探测在当前周期顺序等待，未来 AI 解析不得直接塞进同一路径；P0-C 测采样延迟。
