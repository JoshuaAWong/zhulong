## 2. 总体架构

```
┌─────────────────────────── 单进程 ───────────────────────────┐
│  主线程：托盘 icon.run()（pystray 消息循环）                    │
│  daemon 线程 A：采集循环（30s）→ collectors → storage → engine │
│  daemon 线程 B：ThreadingHTTPServer.serve_forever()（面板只读） │
└──────────────────────────────────────────────────────────────┘
```

模块边界（一句话版）：

- **collectors** 只产出 `(key, value, label)` 数据，不知道规则的存在
- **rules** 只读上下文返回"是否触发"，不知道动作细节
- **actions** 只执行已确认的触发并自行降级，不读指标
- **engine** 是唯一持有运行态（since / cooldown / muted_until）的地方
- **storage** 是唯一碰 SQLite 的地方
- **web** 只从 storage 查询，永不调用 engine / actions

## 4. 线程模型（硬约束，实现时不得偏离）

| 线程 | 职责 | 阻塞点 |
|---|---|---|
| 主线程 | pystray `icon.run()`（Win32 消息循环） | 常驻 |
| daemon A | 采集 → 写库 → 规则评估 → 动作；每周期刷新心跳 | sleep 30s |
| daemon B | `ThreadingHTTPServer.serve_forever()` | 常驻 |

- 启动顺序：日志初始化 → daemon A、daemon B → 主线程 `icon.run()`
- 退出顺序（托盘菜单"退出"）：写 `stopped.intent` → `server.shutdown()` → `icon.stop()` → 进程退出
- SQLite：**单连接跨线程复用**（`check_same_thread=False`）+ `PRAGMA busy_timeout=5000`；WAL 模式下读不阻塞写、写由 busy_timeout 串行化（实现比"每线程独立连接"更简单，安全性由 WAL+超时保证）
- 线程顶层必须包异常处理：`threading.excepthook` 兜底 + 采集循环内 try/except，异常记日志 + 置托盘为灰色（心跳异常态），绝不静默死亡

修订来源：架构评审 A1（线程模型未定死是最大缺陷）、A6/落地评审#3（pythonw 黑洞：入口第一行配 `RotatingFileHandler`，显式重定向 stdout/stderr，主函数包 `logging.exception`）。

## 5. 数据模型

```sql
CREATE TABLE metrics (
  ts        TEXT NOT NULL,     -- 墙钟 UTC ISO8601
  collector TEXT NOT NULL,     -- 'memory' / 'process' / 将来 'gpu'…
  key       TEXT NOT NULL,     -- 'commit_percent' / 'hyphelper_commit_gb'…
  value     REAL,
  label     TEXT DEFAULT ''    -- 维度：'gpu0' / 'C:' / PID 等（为未来扩展预留）
);
CREATE INDEX idx_metrics_ck_ts ON metrics(collector, key, ts);
CREATE INDEX idx_metrics_ts    ON metrics(ts);          -- 清理专用

CREATE TABLE events (
  ts     TEXT NOT NULL,
  rule   TEXT NOT NULL,      -- 'hyphelper_leak' / 'commit_high' / 'heartbeat_lost'…
  action TEXT NOT NULL,      -- 'kill_process' / 'toast' / 'muted' / 'degraded'
  detail TEXT               -- JSON：进程名/PID/当时的值/降级原因
);
CREATE INDEX idx_events_ts ON events(ts);
```

- `PRAGMA journal_mode=WAL`（抗看门狗强杀损坏，必开）；清理后 `PRAGMA wal_checkpoint(TRUNCATE)`
- 数据量预估：约 8 键 × 2880 采样/日 ≈ 2.3 万行/日，30 天 ≈ 69 万行 < 100MB，**不需要预聚合**；24h 曲线用 `GROUP BY` 5 分钟桶（288 点）实时聚合即可
- 写入：每周期单事务 `executemany` 批量提交
- 清理：每日一次 `DELETE WHERE ts < cutoff`（30 天）
- 修订来源：架构评审 C（索引与量级估算）、B（`label` 列现在就加，避免未来加列迁移破坏"schema 永不改"承诺）

## 6. 采集器规范

约定：每个 collector 是一个 py 文件，模块级暴露一个 dict，registry 用 `pkgutil.iter_modules` 自动发现——**扔文件进目录即生效，无手工注册**（修订来源：架构评审 B"假余地"）。

```python
# collectors/xxx.py 的约定形态
COLLECTOR = {
    "name": "memory",
    "interval": 1,                     # 每 N 个基础周期跑一次
    "collect": lambda cfg: [           # 返回 [(key, value, label), ...]
        ("commit_percent", psutil.swap_memory().percent, ""),
        # ...
    ],
}
```

关键事实（落地评审核实）：**Windows 上 `psutil.swap_memory()` 就是 commit charge**——内部调 `GetPerformanceInfo`，`total=CommitLimit×PageSize`、`used=CommitTotal×PageSize`，与 PowerShell `Get-Counter "\Memory\Committed Bytes"/"\Memory\Commit Limit"` 完全对齐。代码注释必须写明这一 Windows 特有语义，防止后续维护者把它"纠正"成 pagefile 用量；`sin/sout` 恒为 0，不使用。

## 7. 规则引擎

规则 = 数据式 dict（首发两条合并在 rules.py，不搞一规则一文件）：

```python
RULE = {
    "name": "hyphelper_leak",
    "every": 1,                      # 每 N 个周期评估一次
    "condition": lambda ctx: ctx.process_commit_gb("HYPHelper.exe") > 15,
    "for_seconds": 0,                # 持续条件窗口（0=立即）
    "enter": 0.85, "exit": 0.80,     # 迟滞阈值（仅高水位规则用）
    "cooldown_seconds": 600,         # 触发后冷却
    "actions": ["kill_process", "toast"],
}
```

引擎状态（全部在 engine，重启丢失可接受）：

- `since[name]`：条件持续起点（`time.monotonic()`；90 秒窗口 = 连续 3 个周期成立）
- `cooldown_until[name]`：冷却截止
- `hysteresis[name]`：当前是否处于"已触发"态（红进 ≥enter，退须 ≤exit，防抖动）
- `muted_until`：暂停动作的全局时间戳，**持久化到单行 kv 表**（托盘"暂停 5 分钟"写它；评估与事件记录照常，动作标记 `muted`）

规则时间判定一律 `time.monotonic()`，落库一律 `time.time()`，严禁混用（休眠唤醒/NTP 校时防护）。唤醒后首个采样周期跳过规则评估。

修订来源：架构评审 A3（防抖）、A5/D（暂停语义与最简实现）、E4（双时钟分离）。

## 8. 动作规范

### 8.1 kill_process（安全链，顺序执行缺一不可）

1. **重读确认**：执行前重新读取该进程 commit，仍超阈值才继续（防采样与执行间的状态变化）
2. **路径校验**：`proc.exe()` 与白名单路径一致（防同名假冒）
3. **身份防竞态**：记录 `proc.create_time()`，kill 前再比对一次（防 PID 复用杀错人）
4. **启动保护**：进程创建时间 < 60 秒的不杀（避开启动瞬时高占）
5. **频次熔断**：同进程 10 分钟内最多 2 次，超限降级为仅 toast + 事件（防与对方守护进程互相拉锯）
6. **异常降级**：`psutil.AccessDenied`/`NoSuchProcess` → toast 提示用户手动处理 + 记 `degraded` 事件，绝不让异常炸掉动作线程
7. 红线：白名单由 config.py 明文维护，**永不收录安全软件进程**；首期不做面板编辑白名单

### 8.2 toast（降级链）

1. `winotify`（纯 Python，免 UAC 无黑窗，`launch` 参数点击打开 `http://127.0.0.1:8890`）
2. 失败 → subprocess 内联 PowerShell（`creationflags=CREATE_NO_WINDOW` 防黑窗）
3. 再失败 → 独立线程 `ctypes MessageBoxW`（阻塞型，放线程里）
4. 全部失败 → 仅记 events（面板可见）

注意：Win11 勿扰/专注助手会吞 toast，部署清单含系统通知设置检查项。

修订来源：架构评审 F（kill 补漏）、落地评审#4（winsdk 系在 3.13 无 wheel，winotify 为唯一稳妥选型，已核实）。

## 9. 托盘

- pystray 0.19.5 + Python 3.13（已核实兼容；**3.14 排除**）
- 图标：Pillow 预生成 3 色 64×64 圆点 + 灰色（心跳异常）共 4 态，字典缓存；改图标/tooltip 直接赋值 `icon.icon` / `icon.title`，不重建 Icon 对象
- tooltip ≤ 127 字符（NOTIFYICONDATA 限制），格式：`烛龙 · commit 62% (53/95GB)`
- Explorer 重启图标自动恢复（pystray ≥0.14.1 内建 TaskbarCreated 处理，无需自处理）
- 菜单：打开面板 / 暂停 5 分钟（写 muted_until）/ 退出（写 stopped.intent）
- 灰色态：心跳文件超过 2 个周期未更新时点亮，同时可被看门狗捕获拉起

## 10. Web 面板（只读红线）

- `ThreadingHTTPServer` 绑定 `127.0.0.1:8890`；**仅 GET，零 POST/执行端点**（防 DNS rebinding 触达）
- 端点：`/`（单页）、`/api/current`、`/api/history?collector=&key=&hours=24`（5 分钟桶聚合）、`/api/events?limit=50`、favicon 返回 204
- MIME 坑规避：`.js/.css/.html` Content-Type 硬编码（Windows 注册表可能把 .js 映射成 text/plain）；响应头 `charset=utf-8`；JSON `ensure_ascii=False`
- Chart.js 单文件 UMD 本地分发（不依赖 CDN；中国网络环境）
- 页面：水位卡片（commit% 大数字+状态色）、24h commit 曲线、白名单进程曲线（多选）、事件时间线

## 11. 部署与自愈

- 解释器：**写死 3.13 的 pythonw.exe 完整路径**（本机另有 3.14，禁用），命令行加 `-X utf8`
- 计划任务 ×2，用 XML 导入注册（显式 `DisallowStartIfOnBatteries=false`、`StopIfGoingOnBatteries=false`，规避 schtasks 默认电池条件坑），均以当前用户运行（`/rl limited`，绝不 SYSTEM——否则托盘不可见）：
  - `Zhulong`：登录自启（onlogon）
  - `ZhulongWatchdog`：每 5 分钟（minute /mo 5）
- 心跳：`state/heartbeat.json` = `{"pid": <pid>, "ts": <epoch>}`，采集线程每周期更新
- 看门狗逻辑：心跳文件缺失或 mtime 距今 > 120 秒 → `taskkill /PID <旧pid>` → 启动新实例；心跳正常 → 无操作
- `stopped.intent`：托盘退出时写入；看门狗见之则不拉起；登录自启任务与手动启动时清除
- 单实例：启动时 `ctypes CreateMutexW("Global\\ZhulongSingleInstance")`，`ERROR_ALREADY_EXISTS` 则立即退出（防看门狗与手动启动竞态双开）
- 安全软件（管家/360）部署指引（写进 README）：首次注册计划任务/AUMID 注册表/PowerShell 子进程会弹窗，点允许；项目目录加入信任区；检查系统通知总开关与勿扰模式

## 14. 扩展指南（写给未来维护者/AI）

- **加监控项**：新建 `collectors/foo.py`，暴露 `COLLECTOR = {"name": ..., "interval": ..., "collect": ...}`，重启即出现在面板（registry 自动发现）。维度数据放 `label`
- **加规则**：在 `rules.py` 加一个 RULE dict（condition 读 ctx 提供的最近指标）
- **加动作**：新建 `actions/foo.py` 暴露 `ACTION = {"name": ..., "run": ...}`；动作必须自带降级、绝不抛异常出线程
- 禁止：web 调 engine/actions；collector 读规则状态；任何绕过 storage 直连 SQLite 的代码

## 15. 实现前风险清单（概率×影响排序）

| # | 风险 | 对策 |
|---|---|---|
| 1 | 误用系统 Python 3.14 运行 | 启动入口写死 3.13 pythonw 全路径 |
| 2 | pythonw 下异常静默（盲飞） | 入口即日志 + excepthook + 托盘灰态 |
| 3 | 管家/360 拦计划任务/PowerShell/杀进程 | 部署指引白名单；引擎永不碰安全软件进程 |
| 4 | schtasks 默认电池条件致看门狗不跑 | XML 导入显式关闭电池限制 |
| 5 | .js MIME 被注册表映射成 text/plain | handler 硬编码 Content-Type |
| 6 | 勿扰模式吞 toast | 部署检查项 + toast 降级链 + 事件表兜底可见 |
| 7 | SQLite 锁冲突 | WAL + busy_timeout（基本清零） |
| 8 | pystray 停更的长期风险 | tray.py 薄封装隔离，可替换 |
