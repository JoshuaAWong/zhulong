## 2. 总体架构

```
┌─────────────────────────── 单进程 ───────────────────────────┐
│  主线程：托盘 icon.run()（pystray 消息循环）                    │
│  daemon 线程 A：采集循环（30s）→ collectors → storage → engine │
│  daemon 线程 B：ThreadingHTTPServer.serve_forever()（面板只读） │
└──────────────────────────────────────────────────────────────┘
```

模块边界（一句话版）：

- **collectors** 只产出 `(key, value, label)` 数据，不知道规则的存在
- **rules** 只读上下文返回"是否触发"，不知道动作细节
- **actions** 只执行已确认的触发并自行降级，不读指标
- **engine** 是唯一持有运行态（since / cooldown / muted_until）的地方
- **storage** 是唯一碰 SQLite 的地方
- **web** 只从 storage 查询，永不调用 engine / actions

## 4. 线程模型（硬约束，实现时不得偏离）

| 线程 | 职责 | 阻塞点 |
|---|---|---|
| 主线程 | pystray `icon.run()`（Win32 消息循环） | 常驻 |
| daemon A | 采集 → 写库 → 规则评估 → 动作；每周期刷新心跳 | sleep 30s |
| daemon B | `ThreadingHTTPServer.serve_forever()` | 常驻 |

- 启动顺序：日志初始化 → daemon A、daemon B → 主线程 `icon.run()`
- 退出顺序（托盘菜单"退出"）：写 `stopped.intent` → `server.shutdown()` → `icon.stop()` → 进程退出
- SQLite：**单连接跨线程复用**（`check_same_thread=False`）+ 模块级 RLock 覆盖 storage 全部读写路径（终审修订：WAL+busy_timeout 只兜文件级竞争，连接级读写混用须靠锁；本地库操作微秒级，粗粒度无害）；WAL 模式下读不阻塞写
- 线程顶层必须包异常处理：`threading.excepthook` 兜底 + 采集循环内 try/except，异常记日志 + 置托盘为灰色（心跳异常态），绝不静默死亡

修订来源：架构评审 A1（线程模型未定死是最大缺陷）、A6/落地评审#3（pythonw 黑洞：入口第一行配 `RotatingFileHandler`，显式重定向 stdout/stderr，主函数包 `logging.exception`）。

## 5. 数据模型

```sql
CREATE TABLE metrics (
  ts        TEXT NOT NULL,     -- 墙钟 UTC ISO8601
  collector TEXT NOT NULL,     -- 'memory' / 'process' / 将来 'gpu'…
  key       TEXT NOT NULL,     -- 'commit_percent' / 'hyphelper_commit_gb'…
  value     REAL,
  label     TEXT DEFAULT ''    -- 维度：'gpu0' / 'C:' / PID 等（为未来扩展预留）
);
CREATE INDEX idx_metrics_ck_ts ON metrics(collector, key, ts);
CREATE INDEX idx_metrics_ts    ON metrics(ts);          -- 清理专用

CREATE TABLE events (
  ts     TEXT NOT NULL,
  rule   TEXT NOT NULL,      -- 'hyphelper_leak' / 'commit_high' / 'heartbeat_lost'…
  action TEXT NOT NULL,      -- 'kill_process' / 'toast' / 'muted' / 'degraded'
  detail TEXT               -- JSON：进程名/PID/当时的值/降级原因
);
CREATE INDEX idx_events_ts ON events(ts);
```

- `PRAGMA journal_mode=WAL`（抗看门狗强杀损坏，必开）；清理后 `PRAGMA wal_checkpoint(TRUNCATE)`
- 数据量预估：约 8 键 × 2880 采样/日 ≈ 2.3 万行/日，30 天 ≈ 69 万行 < 100MB，**不需要预聚合**；24h 曲线用 `GROUP BY` 5 分钟桶（288 点）实时聚合即可
- 写入：每周期单事务 `executemany` 批量提交
- 清理：每日一次 `DELETE WHERE ts < cutoff`（30 天）
- 修订来源：架构评审 C（索引与量级估算）、B（`label` 列现在就加，避免未来加列迁移破坏"schema 永不改"承诺）

## 6. 采集器规范

约定：每个 collector 是一个 py 文件，模块级暴露一个 dict，registry 用 `pkgutil.iter_modules` 自动发现——**扔文件进目录即生效，无手工注册**（修订来源：架构评审 B"假余地"）。B3 起 discover 逐模块容错：坏文件记日志跳过，同名冲突记 warning。

```python
# collectors/xxx.py 的约定形态
COLLECTOR = {
    "name": "memory",
    "interval": 1,                     # 每 N 个基础周期跑一次（B3 起由调度器统一分频，
                                       # 采集器内不得再私自分频；gpu=2、proctop=4，缺省 1）
    "collect": lambda cfg: [           # 返回 [(key, value, label), ...]，每次调用即采
        ("commit_percent", used / limit * 100, ""),
        # ...
    ],
}
```

**B3 存储减量**：proctop label 的 cmdline 截断 200 字符（超长 label 曾占 DB 日写入 87%）；常量键（mem_total_gb / pagefile_total_gb / commit_limit_gb / gpu_mem_total）on-change 落库——采集器内模块级 last-value 比对，同值不写、每日兜底一行、重启首采必写，面板 `latest()` 语义不变。

**B4 IO 大户语义修正**：`io_top_mb`（进程生命周期累计量，长跑进程永久霸榜）改名 **`io_top_mb_s`**，取 `_IO_PREV` 差分速率 MB/s（首采只建基线不出数）；`_PROC_CACHE`/`_IO_PREV` 条目带 create_time 校验，PID 复用时丢弃旧计数（psutil cpu_percent 内部差分同赖此缓存）。旧 key 历史行留存 DB 但面板不再读取。

**网关选取（v1.5 修正）：** net 采集器的默认网关改解析 `route print -4`（GBK 解码）——取目的/掩码均为 0.0.0.0 的默认路由行中跃点数最小者的网关列（旧实现 ipconfig 正则抓「默认网关」，多网卡/VPN 场景抓错或抓不到，ping_gw_ms 全灭）。网关模块级缓存：命中直接用，仅 ping 网关失败才重新解析。

**关键事实（2026-10-04 实测修正，推翻落地评审旧结论）：** 新版 psutil 的 `swap_memory()` 在 Windows 上返回的是**页面文件用量**而非 commit charge——本机实测 total=62GB（页面文件）vs 系统 commit 上限 93GB。旧版 psutil 曾以 swap_memory 表示 commit（issue #1921 时代），行为已在版本更新中改变。**commit charge 必须经 ctypes 调 `GetPerformanceInfo` 获取**（`CommitTotal/CommitLimit × PageSize`），与 PowerShell `Get-Counter` 完全同源（对账误差 <0.1%，AC-5 实测通过）；`swap_memory()` 则作为页面文件指标的数据源正确使用。教训：**"核实过的库行为"也会随版本失效，AC 验收不该跳过真机对账。**

## 7. 规则引擎

规则 = 数据式 dict（首发两条合并在 rules.py，不搞一规则一文件）：

```python
RULE = {
    "name": "hyphelper_leak",
    "every": 1,                      # 每 N 个周期评估一次
    "condition": lambda ctx: ctx.process_commit_gb("HYPHelper.exe") > 15,
    "for_seconds": 0,                # 持续条件窗口（0=立即）
    "enter": 0.85, "exit": 0.80,     # 迟滞阈值（仅高水位规则用）
    "cooldown_seconds": 600,         # 触发后冷却
    "actions": ["kill_process", "toast"],
}
```

引擎状态（全部在 engine，重启丢失可接受）：

- `since[name]`：条件持续起点（`time.monotonic()`；90 秒窗口 = 连续 3 个周期成立）
- `cooldown_until[name]`：冷却截止
- `hysteresis[name]`：当前是否处于"已触发"态（红进 ≥enter，退须 ≤exit，防抖动）
- `muted_until`：暂停动作的全局时间戳，**持久化到单行 kv 表**（托盘"暂停 5 分钟"写它；评估与事件记录照常，动作标记 `muted`）。v1.5 起**存墙钟**（重启后仍生效）；启动读回时 <1e9 的值视为旧版 monotonic 残留，丢弃

规则窗口/冷却一律 `time.monotonic()`，静音与落库一律 `time.time()`，严禁混用（休眠唤醒/NTP 校时防护）。唤醒后首个采样周期跳过规则评估。

修订来源：架构评审 A3（防抖）、A5/D（暂停语义与最简实现）、E4（双时钟分离）。

## 8. 动作规范

### 8.1 kill_process（安全链，顺序执行缺一不可）

0. **NEVER_KILL 硬阻断**（v1.5）：目标名命中 core/anomaly.NEVER_KILL 直接返回 blocked，防配置事故——即使管理员误把 explorer.exe 配进名单也杀不了
0.5 **名单解析**：先查 WATCH_PROCESSES；查不到则回落 AUTOKILL 名单（v1.5 打通，元素允许字符串或 dict 带 path_contains，不配 path_contains 则无路径校验），阈值取 ANOMALY_REDLINE_GB（20GB）
1. **重读确认**：执行前重新读取该进程 commit，仍超阈值才继续（防采样与执行间的状态变化）
2. **路径校验**：`proc.exe()` 与白名单路径一致（防同名假冒）
3. **身份防竞态**：记录 `proc.create_time()`，kill 前再比对一次（防 PID 复用杀错人）
4. **启动保护**：进程创建时间 < 60 秒的不杀（避开启动瞬时高占）
5. **频次熔断**：10 分钟内最多 2 次，超限降级为仅 toast + 事件（防与对方守护进程互相拉锯）。v1.5 起 kill_times 走 kv 表——自动通道与面板手动 kill 共用同一份计数；B2 起**按进程名分桶**（kv `{name: [ts...]}`，A 杀满不挤占 B 额度；旧格式纯列表视为无 per-process 历史）
6. **异常降级**：`psutil.AccessDenied`/`NoSuchProcess` → toast 提示用户手动处理 + 记 `degraded` 事件，绝不让异常炸掉动作线程
7. 红线：白名单由 config.py 明文维护，**永不收录安全软件进程**；首期不做面板编辑白名单

### 8.2 toast（降级链）

1. `winotify`（纯 Python，免 UAC 无黑窗，`launch` 参数点击打开 `http://127.0.0.1:8890`）
2. 失败 → subprocess 内联 PowerShell（`creationflags=CREATE_NO_WINDOW` 防黑窗；B2 起 title/body 的单引号双写转义——进程名/cmdline 含 `'` 属注入面）
3. 再失败 → 独立线程 `ctypes MessageBoxW`（阻塞型，放线程里）
4. 全部失败 → 仅记 events（面板可见）

注意：Win11 勿扰/专注助手会吞 toast，部署清单含系统通知设置检查项。

修订来源：架构评审 F（kill 补漏）、落地评审#4（winsdk 系在 3.13 无 wheel，winotify 为唯一稳妥选型，已核实）。

## 10. Web 面板（只读 + 令牌动作通道，v1.3 修订；v1.5 B2 加固）

- `ThreadingHTTPServer` 绑定 `127.0.0.1:8890`；**仅 GET + 一个令牌守卫的 POST /api/action**（红线 v1.3 修订：零"配置写"端点不变；动作通道=CSRF token（GET /api/action_token 仅同源可读）+ Host/Origin 校验（防 DNS rebinding）+ 动作白名单（kill_process 仅限白名单进程 / throttle_on|off / v1.6 增 mem_trim、restart_service——target 须在对应 config 白名单、与自动通道共用熔断；autoclean_on|off 温和处置总开关）+ kill 七步安全链）
- 防线口径（B2）：**GET/POST 共用 Host 校验**（此前 GET 系无检查，DNS rebinding 可读令牌）；Origin 校验改 urlparse 取 hostname 与 {127.0.0.1, localhost} **精确比较**（startswith 会被 `http://127.0.0.1.evil.com` 绕过），端口不强制；GET 参数钳制（hours≤744 / bucket≥60 / limit≤500，解析失败 400 非 500）；非 dict JSON body → 400

## 17. 限流器（v1.3）

- **机制**：对配置内进程施加运行时属性（nice 优先级 + cpu_affinity 绑核），不写注册表不动文件，进程退出即蒸发，天然可逆
- **规则双层**：`config.THROTTLE_DEFAULTS` 出厂规则（只读，预填 ToDesk/QQPCTray/AweSun/sunloginclient → below_normal + tail:N 核）；`data/throttle_override.json` 用户覆盖（gitignore，存在即生效）
- **状态持久**：enabled 写 kv（托盘/面板动作通道可切）；`throttle_applied` 已施加清单写 kv——restore 按清单还原（不按现行规则），override 删规则后已戴镣铐的进程也能摘
- **执行**：挂 `scheduler.run_cycle` 末尾分频（THROTTLE_INTERVAL_CYCLES=4）幂等应用（已是目标态跳过；变化才记事件 rule="throttle"）；B4 起规则一次取值（此前在 process_iter 循环体内，200 进程读 200 次 override.json）
- **红线**：priority 仅 normal/below_normal；cores 合法性校验（tail:N / spread:N 错峰 / 核号列表，按 cpu_count 动态求）；AccessDenied 跳过；永不处理自身 PID
- **schema 校验（B4）**：override 规则逐条过 `validate_rules`（name 非空 / priority ∈ 白名单 / cores 为 tail:N 或核号列表），非法规则跳过并记一次 `throttle/skip` 事件（内容不变不重复记），不再让 ValueError 炸掉整轮限流
- **skip 可见性（B4，终审后修订）**：apply/restore 遇 AccessDenied（自保护进程）记 `throttle/skip` 事件（此前完全静默）；**状态变化才记**——denied 集合与上轮相同不重复记（QQPCTray 永远 denied，每轮记会变成每天 720 条噪声）
- **退出还原（B4）**：托盘退出路径统一调 `throttle.restore()`，被限流进程不残留 BelowNormal+绑核；看门狗崩溃重启路径无法 restore（进程意外死亡没机会清理，清单在 kv 里，下次正常退出可还原）
- **已知边界**：腾讯电脑管家等自保护进程拒绝非提权进程的读写（apply 记 skip 事件）——不为限流提权，管家类问题走精简/替换路线

## 18. 通用异常进程跟踪（v1.4，取代 HYPHelper 专用白名单）

- **采集**：proctop 每 2 分钟 Top5 commit 落库（label=name|pid|cmdline），天然形成各进程时间序列
- **判定**（`core/anomaly.py` 纯函数）：30 分钟窗口 增长 >4GB 且 >50%（当前 >8GB）→ suspect；当前 >20GB 且非保护名单 → redline。NEVER_KILL 豁免：系统关键/安全软件/烛龙自身/ZenlessZoneZero.exe（游戏）。v1.5：序列键 name→**name|pid**（同名多实例各自成序，轮换进出 Top5 不互相污染）；series_from_db 补 key IN 过滤（cpu_top_pct 等行不混入）；NEVER_KILL 校验与判定在剥 pid 的纯 name 上做，输出归并纯 name（同名多实例取 current_gb 最大者）
- **规则**：`anomaly_leak`（condition=ctx.anomalies 非空，cooldown 600s，actions=["toast"] 默认仅告警）；AUTOKILL 名单（默认空）按名生成动态 kill 规则（仍走七步安全链）；触发时 scheduler 动态填充 toast 详情与事件 anomaly 字段
- **展示**：/api/current `_meta.anomalies`；面板大户榜红标"⚠ 疑似泄漏"+朱批记事呈现
- **红线告警环比抑制（v1.5 B1，终审修订）**：redline 不看增长，稳态超线进程会在每次冷却到期重复通知。抑制语义：kv `redline_notified`（`{纯name: 上次通知时 current_gb}`），仅 `current_gb > 上次值 + 1GB`（REDLINE_RENOTIFY_STEP_GB）才再放行 toast，首次越线必报；每周期 prune——**序列在但最新值跌破红线**才清条目（回落后再涨可再报）；**序列不存在（跌出 Top5）保留记录**（终审修订：边界震荡进程回榜仍按环比语义，不按首次越线重报）；suspect 不受抑制；事件照记 `suppressed:redline_repeat`，仅 toast 被抑制；kv 损坏 fail-open 允许通知；autokill 规则与面板红标不经过此过滤
- **首例实战**：上线即检出 WmiPrvSE.exe 41.5GB 红线泄漏（2026-10-07）

## 19. 温和资源回收与关键进程识别（v1.6）

定位：白名单内、fail-closed、可逆可开关的温和处置。同步修订需求文档非目标第一条（原"不做系统清理/优化/加速"收敛为不做注册表/磁盘/加速软件式清理）。**kill 七步链零改动、零新依赖（ctypes+psutil 全现成）**；页面文件由系统自动回收，烛龙不做任何页面文件操作。

### 19.1 关键进程识别 `core/protect.py`

- `name_blocked(name)`（无 Process 对象，安全链枚举前调用）与 `is_critical(name, proc)` 五信号按序短路：**安全软件名单** SAFE_SOFTWARE（管家/360/火绒/Defender，红线"永不处置"代码化）→ **NEVER_KILL ∪ NEVER_TOUCH_EXTRA**（顺手补漏 smss/wininit/fontdrvhost）→ **SYSTEM 账户**（username 含 NT AUTHORITY）→ **System32/SysWOW64 路径** → **前台窗口**（ctypes GetForegroundWindow→pid；trim 前台进程会立刻引发换页卡顿）
- **fail-closed**：exe 读不到/为空一律判关键（blocked:exe_unreadable，镜像 kill 路径校验语义）；username 读不到交给路径信号兜底、不误伤
- kill 链不用本模块（继续 NEVER_KILL 入口硬阻断，职责分离）。识别边界：不做数字签名校验（fail-closed 下误放行为零、误拦截只是少清一个进程）
- 真机验证：wudfhost.exe（SYSTEM 账户）→ blocked:system_account；explorer 误配白名单 → blocked:never_kill

### 19.2 内存回收 `memtrim.py` + `actions/mem_trim.py`

- 机制：`OpenProcess(PROCESS_SET_QUOTA|PROCESS_QUERY_LIMITED_INFORMATION)` → `EmptyWorkingSet` 挤出物理内存页（进程不中断不丢数据，下次访问从待备列表快速调回）。**如实分工：只降 working set 不减 commit**——泄漏处置仍归 WATCH/AUTOKILL kill 链
- 安全链（镜像 kill 链序，动作换成 trim）：名单级硬阻断 → kv 熔断（`trim_times` 按名分桶，`max_trims_per_10min`）→ 重读水位（同名取 wset 最大者，低于 `min_ws_gb` 跳过；枚举跳过自身 PID）→ `protect.is_critical`（SYSTEM/系统路径/前台，fail-closed）→ 存活时长 `min_age_s` → 路径校验 fail-closed → create_time 竞态防护 → trim → 记账（返回前后 ws 对比，供事件审计）
- 巡检 `apply_if_due` 挂 run_cycle 尾部（限流器之后，同样 try/except 包裹）：分频 `interval_cycles=2`（1 分钟）；kv `autoclean_enabled` 总开关（缺省取 `MEM_TRIM.enabled`）；**压力门槛** `min_mem_percent=60`——物理内存不紧张整轮跳过（无压力不折腾，Windows 空闲时自己管理待备列表）；事件按状态变化记录（trimmed 每次记，skip 同态不重复记——B1 告警风暴教训）
- 面板手动走同一条链与熔断（actions/mem_trim 薄转发 / server 直调 trim_once）
- 真机验证：3.01GB 测试进程 trim 后 0.00GB（psutil 独立回读，非自证）

### 19.3 泄漏服务重启 `actions/restart_service.py`

- 白名单 `RESTART_SERVICES`（出厂空 = 只告警不动手）；**SERVICES_NEVER_RESTART 硬阻断**（rpcss/dcomlaunch/plugplay/power/lsm/samss，误配白名单也动不了）
- 熔断 1 次/小时（`restart_times` 按服务名分桶，`core/freq_cap.py` 公共件），**发起即记账**——start 失败也占额度，防规则冷却到期反复敲打半死服务
- 执行：`win_service_get`（不存在 skipped:not_found）→ status 非 running 跳过 → `stop()` 轮询 30s（超时 degraded:stop_timeout，服务多半还在缓停不再强动）→ `start()` 轮询 30s（失败重试 2 次间隔 5s，仍失败 `degraded:start_failed`——服务躺着面板可见、人工拉起）。等待循环 monotonic、kv 熔断墙钟（与 kill 链口径一致）
- 触发：`rules._restart_rules` 动态规则（`trigger_processes` 命中 ctx.anomalies 即重启宿主服务，镜像 AUTOKILL 模式）；params `auto=True` 时动作内检查总开关，面板手动不受限
- 依据：服务宿主泄漏（WmiPrvSE 案例）的正确处置是重启服务——杀进程连坐同宿主全部服务

### 19.4 限流错峰 `spread:N`（throttle.py）+ 单核饱和告警

- cores 第三种写法：`assign_cores` 按规则顺序从最高核向下各切 N 核连续块，**规则间不重叠**（根治出厂四规则全 tail:N 叠在同一组尾部核）；游标下限钳在 `cpu_count//2`（不侵入前半核区；小 CPU 超量回落共享下限块）；分配只依赖规则列表顺序 → 确定性 → 幂等不变
- 出厂规则改 spread:2（16 核机器四规则落 [14,15]/[12,13]/[10,11]/[8,9]，真机验证）；`tail:N` 与核号列表语义不变（向后兼容 override）；restore 零改动
- `single_core_hot` 规则：cpu_max_core ≥95% 持续 90s 且 cpu_percent <70%（多进程挤核特征——总值不高但一样卡）→ toast；**只告警不自动绑核**（非白名单进程不动，处置留给限流错峰）

### 19.5 面板与总开关

- 动作白名单扩 4：`mem_trim` / `restart_service`（target 服务端比对对应白名单；面板手动与自动通道共用 kv 熔断，不绕过）/ `autoclean_on` / `autoclean_off`
- kv `autoclean_enabled` 总开关**只闸自动通道**（memtrim 巡检 + restart 动态规则动作内检查），面板手动动作不受限
- `/api/current` `_meta.autoclean`（enabled + 两个名单）；前端"温和处置"卡片（事件委托 + data-target 属性防 onclick 逃逸；服务重启两段式确认；改前端已 bump ?v=5）
