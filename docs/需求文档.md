## 1. 背景

2026-10-02 真实事故（本项目的直接动因）：

- 米哈游启动器组件 `HYPHelper.exe` 泄漏 31.9 GB commit，腾讯电脑管家 `qmlauncher.exe` 泄漏 10.9 GB，系统提交内存（commit）耗尽（85.6/95.2 GB）。
- 连锁后果：《绝区零》进场景时内存分配失败闪退（异常码 0）、桌面合成器饿死黑屏、向日葵/LosslessScaling/msedgewebview2 连环崩溃。
- 手动结束泄漏进程后全部恢复。**泄漏未根治，必然复发**，且本机兼任游戏机与远程控制机（向日葵/GameViewer/ToDesk），桌面崩了连远程都难救。

这类"平时看不到的数值"（commit 水位、进程异常增长）目前没有任何工具持续记录和守护，出问题只能事后人工取证。烛龙就是把这个取证和守护能力常态化。

## 2. 目标 / 非目标

**目标**

1. 持续记录平时不可见的系统数值（首发：commit 虚拟内存水位），可回溯历史曲线。
2. 对已知问题自动处置（白名单机制，首发：HYPHelper 泄漏自动结束）。
3. 对未知异常主动通知（Windows toast），把"事后排查"变成"事中感知"。
4. 架构为后续扩展（GPU / 磁盘 / 网络 / 各类额度监控）留出真实可用的余地。

**非目标（明确不做）**

- 不做注册表清理、磁盘垃圾清理、"加速软件"式系统优化；温和资源回收仅限白名单内、fail-closed、可逆可开关（v1.6 D32 修订，原表述"不做系统清理/优化/加速功能"）。
- 不做多机监控、不做企业级告警体系（值班/升级/静默策略）。
- 不做通用进程管理器；kill 仅限白名单。
- 面板不提供任何配置写端点（动作通道除外，见 D13/D32）。
- 不打包发行（源码即部署，改代码即时生效）。

## 3. 用户与典型场景

单用户：本机管理员（Windows 11 Pro 26200，32GB 内存 + 64GB 页面文件，非专业开发者，AI 辅助维护）。

| 编号 | 场景 | 烛龙的行为 |
|---|---|---|
| S1 | HYPHelper 泄漏复发，commit 缓慢爬升 | 自动结束该进程 + toast 告知 + 事件落库，游戏/桌面无感 |
| S2 | 游戏闪退/电脑卡顿，用户问 AI 排查 | AI 读取烛龙的曲线与事件表，直接给出结论（复用 2026-10-02 的取证链路） |
| S3 | 平时瞥一眼系统状态 | 托盘图标颜色 + tooltip 即可，无需打开任何窗口 |
| S4 | commit 逼近上限但原因不明 | 面板看 24h 曲线趋势 + 白名单进程曲线，锁定元凶 |
| S5 | （未来）想盯 GPU / 磁盘 / token 额度 | 写一个新 collector 文件扔进目录即生效 |

## 4. 功能需求

- **FR-1 采集**：默认 30 秒周期，采集系统 commit（used/limit/percent）、物理内存、页面文件、白名单进程的 commit；每个周期更新心跳文件。
- **FR-2 存储**：SQLite（WAL 模式）通用窄表；保留 30 天，每日自动清理。
- **FR-3 规则·白名单泄漏处置**：白名单进程 commit 超阈值（首发 HYPHelper > 15GB）→ 重读确认 + 进程身份校验 → 结束进程 → toast + 事件落库；同一进程 10 分钟内最多自动处置 2 次，超限降级为仅通知。
- **FR-4 规则·高水位告警**：总 commit ≥ 85% 持续 90 秒 → toast + 事件；回落 ≤ 80% 才解除（迟滞）；同规则冷却 600 秒。
- **FR-5 通知**：Windows 原生 toast，点击打开面板；通知失败按降级链处理并记日志。
- **FR-6 托盘**：图标四态（绿 <70% / 黄 70~85% / 红 ≥85% / 灰=采集心跳异常）；tooltip 显示实时百分比；菜单：打开面板 / 暂停 5 分钟 / 退出。
- **FR-7 面板**：`http://127.0.0.1:8890`，只读；当前水位卡片 + 24h commit 曲线（5 分钟桶）+ 白名单进程曲线 + 事件历史列表。**（已实现，v1.1 扩展为：昼夜双态主题、24h/7天/30天区间切换、全中文标注、内存三层分离展示、事件语义标记、待处理建议、路径展示）**
- **FR-8 自愈**：登录自启 + 每 5 分钟看门狗（基于心跳判定"死亡或卡死"）；单实例互斥；用户主动退出后看门狗不得再拉起。
- **FR-9 扩展机制**：collector / rule / action 三类扩展点目录自动发现；新增指标不改表结构（`label` 维度列）。
- **FR-10 诊断入口**：提供 CLI 查询命令（最近 N 小时水位摘要 + 事件列表），供用户直接使用或 AI 调用。
- **FR-11 暂停语义**：暂停 5 分钟仅静音"动作"（kill/toast），采集与入库照常，触发记录照常（action 标记为 muted）。

## 5. 非功能需求

- **NFR-1 资源占用**：常驻内存 < 80MB；空闲 CPU < 1%；面板仅监听 127.0.0.1，不上传监控数据；默认仅网关与公网 DNS 的 ICMP ping（可关闭）。
- **NFR-2 安全红线**：面板除只读 GET 外仅开放令牌守卫的 `POST /api/action` 动作白名单（CSRF token + Host/Origin 校验）；白名单永不收录安全软件进程；kill 前必须重读水位 + 校验进程创建时间，配置 `path_contains` 的条目还须通过路径校验；不碰 HKLM、不求提权、不注入、不读他进程内存。
- **NFR-3 可维护性**：依赖限定 4 个纯 pip 包（psutil、pystray、Pillow、winotify）；所有可调参数集中在 config.py 一个文件；源码 UTF-8、日志 UTF-8 滚动文件。
- **NFR-4 健壮性**：任一线程异常不得静默死亡（顶层异常钩子 + 日志 + 托盘变灰）；时间窗口判定用单调时钟、落库用墙钟，两者不混用；休眠唤醒后首个采样周期跳过规则评估。
- **NFR-5 环境兼容**：安装时自动发现 Python 3.13+ 或接受环境变量指定，python/pythonw 同目录；运行、看门狗与托盘重启复用当前实例解释器，不因 PATH 变化换用另一套 Python；计划任务以当前用户身份运行（非 SYSTEM）；部署指引包含安全软件（管家/360）白名单步骤与系统通知（勿扰模式）检查项。

## 6. 验收标准

| 编号 | 验收项 | 通过判据 |
|---|---|---|
| AC-1 | 泄漏处置链路 | 用 mock 进程占用 commit 超阈值 → 规则触发 → 进程被结束 + toast 弹出 + events 落库 |
| AC-2 | kill 无副作用 | 自动结束 HYPHelper 后，重新打开 HoYoPlay 功能正常 |
| AC-3 | 自愈 | 强杀烛龙进程 / 模拟卡死（暂停心跳）→ 看门狗在下一执行周期内拉起（最坏 ≈ 5 分钟 + 120 秒心跳阈值），且全系统仅一个实例 |
| AC-4 | 退出语义 | 托盘退出后看门狗不再拉起；重启电脑后登录自启恢复 |
| AC-5 | 数据正确性 | 面板 commit 百分比与 PowerShell `Get-Counter "\Memory\Committed Bytes"/"\Memory\Commit Limit"` 对齐（误差 < 1%） |
| AC-6 | 扩展性 | 新写一个 mock collector 文件放入目录，不改动任何其他文件，面板即出现新指标 |
| AC-7 | 资源达标 | 挂机 24 小时后内存 < 80MB、CPU 空闲占用 < 1%、数据库体积符合预估（< 100MB/30天） |

## v1.5 增量需求（2026-10-11，批次 B1：红线告警环比抑制，已实现）

- **D28 红线告警环比抑制**：redline 级告警（不看增长，稳态超线进程每 10 分钟冷却到期就重复通知——线上 WmiPrvSE 稳态 ~50GB 致 457 条事件中 443 条噪声）改为环比语义——kv 表 `redline_notified` 记每进程上次通知值（JSON `{纯 name: current_gb}`），仅当 current_gb > 上次通知值 + 1GB 才再次 toast；首次越线必报。生命周期闭环：进程最新值跌破红线（≤20GB）或消失即清除 kv 条目，回落后再涨按首次越线再报。suspect 级不受抑制（本来就看增长）。抑制的只是重复 toast，事件照记（`suppressed:redline_repeat`，审计轨迹），面板红标不受影响（面板走自己的 detect，不过滤）。kv 损坏 fail-open 为无历史（允许通知——通知缺失比通知风暴危险）

  - GET 系端点补 Host 校验（此前 /api/action_token 等无 Host 检查，DNS rebinding 场景远端网页可读动作令牌）；Host/Origin 校验抽共用方法，Origin 改 urlparse 取 hostname 精确比较（修 startswith 被 `http://127.0.0.1.evil.com` 绕过），端口不强制

## v1.6 增量需求（2026-10-12，温和资源回收，已实现）

- **D32 温和资源回收 + 关键进程识别**（同步修订非目标第一条：白名单内温和回收放行，注册表/磁盘/加速软件式清理仍不做）：
  - **关键进程识别 `core/protect.py`**：多重信号 fail-closed（识别不了的一律当关键进程对待，绝不误伤）——安全软件名单（管家/360/火绒/Defender，红线代码化）→ NEVER_KILL∪补充（顺手补漏 smss/wininit/fontdrvhost）→ SYSTEM 账户 → System32/SysWOW64 路径（exe 读不到一律判关键）→ 前台窗口进程（ctypes GetForegroundWindow，trim 前台进程会立刻引发换页卡顿）。kill 链继续用 NEVER_KILL 入口硬阻断，职责分离。识别边界：不做数字签名校验（fail-closed 下误放行为零、误拦截只是少清一个进程，代价不对称可接受）
  - **内存回收 `memtrim.py`**：对白名单后台进程调 EmptyWorkingSet 回收物理内存（不杀进程不丢数据）；巡检镜像限流器成熟模式（kv 总开关 `autoclean_enabled` + 分频 1 分钟 + 物理内存压力门槛 `min_mem_percent`=60 无压力不折腾 + 事件按状态变化记录防刷屏）；安全链镜像 kill 链（名单硬阻断→频次熔断→重读 wset 水位→关键进程/前台阻断→存活时长→路径校验 fail-closed→create_time 竞态防护→最小权限 OpenProcess）。如实分工：只降物理内存不减 commit，泄漏处置仍走 WATCH/AUTOKILL kill 链；页面文件由系统自动回收，烛龙不做任何页面文件操作
  - **泄漏服务温和重启 `actions/restart_service.py`**：白名单服务 stop→start（服务宿主泄漏的正确处置是重启服务不是杀进程，杀了连坐同宿主服务）；关键服务硬阻断（rpcss/dcomlaunch/plugplay/power/lsm/samss，误配白名单也动不了）；频次熔断 1 次/小时且发起即记账（防规则冷却到期反复敲打半死服务）；start 失败重试 2 次仍失败记 degraded:start_failed（面板可见、人工拉起）；出厂白名单空 = 只告警不动手；触发走规则引擎（trigger_processes 命中异常判定即重启宿主服务，镜像 AUTOKILL 模式），自动通道受总开关闸、面板手动不受限
  - **限流错峰 `spread:N`**：cores 新写法——按规则顺序从尾部向下各切 N 核连续块、规则间不重叠（根治出厂四规则全用 tail:N 的叠核）；游标钳在核数一半不侵入前半核区（小 CPU 超量回落共享下限块）；出厂规则改 spread:2；旧 tail:N/核号列表语义不变（向后兼容 override）
  - **单核饱和告警 `single_core_hot`**：最忙核 ≥95% 持续 90 秒且总占用 <70%（多进程挤核特征——总值不高但一样卡）→ toast；只告警不自动绑核（非白名单进程不动）
  - **面板**：动作白名单扩 mem_trim / restart_service（target 须在对应白名单，与 kill 同款服务端比对；面板手动与自动通道共用同一份熔断计数）/ autoclean_on / autoclean_off（总开关只闸自动通道）；`_meta` 挂 autoclean 状态；前端"温和处置"卡片（总开关 + 逐进程"整理" + 服务"重启"两段式确认，目标走 data-target 属性防 onclick 逃逸）
  - **熔断公共件 `core/freq_cap.py`**：trim/restart 与 kill 的分桶熔断逻辑同构，抽公共小模块只给新动作用（kill 链红线文件不回改）
